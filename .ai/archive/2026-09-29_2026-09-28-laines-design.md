# L.AI.nes: parallel-lanes tool (design, in progress)

**Status:** brainstorming. Decisions below are agreed; sections marked *Proposed* still need
review. Nothing is implemented yet. Next step after the design is approved: write the
implementation plan.

## Goal

A kit for running parallel work lanes on any git project. A "container" directory holds several independent clones
("lanes") of one repo, a shared `.ai/` that every lane inherits, and a status board lanes report
to while a top-level session creates, monitors, and tears lanes down.

Source material for the kit (the original scripts, templates, and runbook, stripped of
project-specific content) lives in `../../reference/`.

## Why lanes exist

Parallel work via worktrees (or shared local setups) collides on **local environment state**:
one task's schema changes break another's DB, caches bleed across tasks, ports clash, and PRs
pick up work from other tasks. A lane is a fully separate clone with its **own isolated local
environment**, so each session keeps its state to itself — while every lane still shares one
knowledge base (the container's `.ai/`).

**Why only `context/` + `plans/` live in a lane:** everything else (`knowledge/`, `guidelines/`,
`lessons/`, and notably `data/` and `audits/`) must outlive any single lane. When a lane is torn
down, a new lane picks up the same `data/` and `audits/` from the container. Don't move these
into lanes.

## Decisions

1. **Standalone npm CLI that bundles dot-ai** *(supersedes "copyable starter kit")*. lAInes is
   not layered onto an existing dot-ai project. `laines init <container> --remote <url>` creates
   a fresh container: runs the bundled `dot-ai` (npm dependency `@ajmarquez99/dot-ai`, invoked
   via its CLI — dot-ai has no programmatic API) to scaffold `.ai/` and wire agent config, then
   layers on lane management: lane-ownership instructions, runbook, board, lane templates,
   `lanes.conf`. Lanes are then managed with `laines create|report|teardown|watch`.
2. **Isolation = built-in primitives + project hooks** (option A). lAInes always owns: a lane
   number, a port block derived from it (`BASE_PORT + N * PORT_STRIDE`), a per-lane env file
   (`LANE_NAME`, `LANE_NUMBER`, `PORT`, a name suffix like `_lane_2` for DBs/caches), and a
   per-lane Docker Compose project name. Stack-specific work (create/drop DB, patch a tracked
   config) lives in project hooks (`post-create`, `pre-teardown`, `post-teardown`).
   **Future (option B):** built-in service adapters (Postgres/MySQL/Redis…) configured in
   `lanes.conf`. Design the hook runner so an adapter is just a packaged hook — adding B later
   must not change the hook contract.
3. **Agent-agnostic, Claude preferred.** The board and files are the coordination channel for
   any agent. Wiring defaults to Claude (`CLAUDE.md`); `--agents claude,codex,gemini|all` wires
   others through dot-ai's existing targets, and the lane-ownership section goes into every
   wired file. Claude-only extras (`SendMessage`, `plansDirectory`) are optional
   enhancements, never required. The agent launch command in lane hints is configurable
   (`AGENT_CMD`, default `claude`).
4. **`.ai/` layout** (unchanged): board at `.ai/context/LANES_BOARD.md`; lanes carry only
   `.ai/README.md`, `.ai/context/`, `.ai/plans/`.
5. **Repos that commit their own `.ai/`** (option A): the repo's `.ai/` is read-only project
   truth for lanes (writable only when the task is itself a project-docs change). Lane-local
   files (`.ai/context/`, `.ai/plans/`, `.ai/README.md`, `.ai/.lane.json`, `CLAUDE.local.md`)
   are hidden via `.git/info/exclude` — never the repo's `.gitignore` — so they never reach a PR.
6. **Explicit lane detection, no upward guessing.** Markers: `<container>/.laines/container.json`
   and `<lane>/.ai/.lane.json` (`{ lane, number, container }`, excluded from git). Lane mode iff
   the lane marker exists at the repo root *and* its `container` path has the container marker;
   otherwise normal dot-ai resolution (repo `.ai/` → `~/.ai/`), no container lookup, no board
   reporting — even for a plain checkout that happens to sit under a container.
7. **Lane-mode resolution:** lane `context/`+`plans/` (lane working state) → repo's committed
   `.ai/` (read; wins on conflict) → container `.ai/` (read; write target for all new durable
   knowledge, guidelines, lessons, `data/`, `audits/`) → `~/.ai/` (index only).
8. **Instruction placement.** Claude: lane-mode block in the container `CLAUDE.md` (with a
   "ignore unless `.ai/.lane.json` exists" guard) + per-lane `CLAUDE.local.md` carrying the lane's
   identity and the detection check. Other agents: the lane-local `.ai/README.md` as fallback;
   `AGENTS.md`/`GEMINI.md` only when the repo doesn't commit them (pending Codex/Gemini research).
9. **Ships a CLI and an MCP server**, mirroring sibling tools (dot-ai, gmail-cli, discord-cli):
   `laines` + `laines-mcp` over one shared command layer.
10. **Name: L.AI.nes** (lanes, with the AI emphasized). The display name in README, docs and
    help text is `L.AI.nes`. Machine identifiers stay dot-free: npm `@ajmarquez99/laines`, bins
    `laines` / `laines-mcp`, repo `laines`, marker dir `.laines/`.
11. **Hooks: checksum approval with a loosenable policy.** Hooks live in `<container>/.laines/hooks/`
    (outside the lane-writable `.ai/`). `hooks.policy` in `.laines/config.json`:
    `approve` (changed/new hook refused at exit 3 with its diff until a human runs
    `laines hooks approve`), `notify` (runs; warns, audit-logs, and posts the new checksum to the
    board), `open` (no check). Agents may always *edit* hooks; policy governs only whether an
    edited hook *runs* without sign-off. Changing policy and approving are CLI-only, never MCP,
    refused in locked mode. `laines hooks status` (read-only, CLI + MCP) shows
    approved/changed/new with diffs.
    **Default for a new container is `notify`**: at install L.AI.nes knows nothing about the
    project's local environment, so agents build the hooks. Once hooks are stable — unchanged
    across the last 3 successful lane creates (threshold configurable) — `create`, `doctor`, and
    the board suggest locking them (`laines hooks approve --lock` → approves current set and sets
    `approve`). L.AI.nes never switches policy on its own; the user can lock at any time, e.g. on
    a project still under active construction.
12. **Teardown is explicit over MCP.** `teardown.mcp` (CLI-only setting): `confirm` (default) —
    the server asks the human via MCP elicitation with a summary (lane, branch, open PRs,
    unpushed work, what gets archived/deleted); decline/no answer = nothing happens; clients
    without elicitation get exit 3 + a board request, completed by a human with CLI
    `laines teardown`. `auto` — no prompt, safety checks still apply. `off` — tool not exposed.
    Reason: a lane that looks done may be the base of stacked PRs or correlated work.
13. **`keep` / `release`.** `laines keep <lane> --reason ...` pins a lane: teardown refused from
    every path (incl. `auto` and CLI `--force`) until `laines release <lane>` (CLI-only). Agents
    may `keep` over MCP (safe direction), never `release`. Shown as 📌 on board and `list`.
14. **Two lane workflows, no `laines open`.** Lanes are always created from the parent container
    session. Then either (a) the user `cd`s into the lane and starts a fresh agent session, which
    auto-loads container `CLAUDE.md` + repo instructions + lane `CLAUDE.local.md`; or (b) the
    parent dispatches a subagent to work in the lane. A subagent inherits the parent's cwd and
    instructions and does NOT auto-load lane/repo instruction files, so `laines brief <lane>`
    (CLI + MCP `laines_brief`) emits a handoff for the subagent prompt: lane identity, absolute
    path, branch, ports, env file to source, instruction files to read in order, lane rules
    (stay in the lane path, `git -C`, report as `<lane>`, no dot-ai init/sync), and the lane's
    board block. `create` prints it on success.
15. **`laines refresh <lane>`** (v1): re-runs `post-create` against an existing lane — needed
    while hooks are still being built under `notify`.
16. **Human-only commands are enforced beyond MCP.** MCP gating does not stop an agent with shell
    access from running the CLI. `laines init` writes Claude permission deny rules for
    `laines teardown`, `laines release`, `laines hooks approve`, `laines hooks policy`, and
    `laines config set` into the container `.claude/settings.json` (covers the parent session and
    its subagents) and `laines create` writes them into each lane's `.claude/settings.local.json`
    (excluded from git; merged if one exists) — container settings do **not** reach a lane.
    Agents must go through MCP, where `teardown.mcp: confirm` applies; humans run these from
    their own terminal. Residual risks documented in `SECURITY.md`: user-level config and
    Claude `Elicitation`/`ElicitationResult` hooks can override answers; `doctor` warns when an
    elicitation hook is visible to a lane.
17. **Elicitation fallback UX.** Some clients declare elicitation but auto-decline. Decline = no
    action (safe), with the message "declined or no response — if you weren't prompted, run
    `laines teardown <lane>` from your terminal". `doctor` reports client elicitation support.
18. **Hook contract.** Executables in `.laines/hooks/` named by event, plus ordered
    `<event>.d/*` (where future built-in adapters drop in — contract unchanged). Events:
    `post-create` (cwd lane; after clone, lane `.ai/`, excludes, env file; re-run by `refresh`;
    failure keeps the lane, marks it `setup-failed` on the board), `pre-teardown` (cwd lane; after
    safety checks, before any archive/delete; failure aborts teardown untouched),
    `post-teardown` (cwd container; failure warns + board "cleanup incomplete"). Env:
    `LANE_NAME`, `LANE_NUMBER`, `LANE_DIR`, `CONTAINER_DIR`, `LANE_PORT_BASE`, `LANE_PORT_COUNT`,
    `LANE_SUFFIX`, `LANE_BRANCH`, `LANE_ENV_FILE`, `LAINES_HOOK`, `LAINES_DRY_RUN`. Exit 0 ok,
    3 = blocked/needs a human (not failure), other = failure. Timeout default 300s
    (configurable). Output captured, returned to agents marked untrusted. `--dry-run` runs no
    hooks, lists which would run and their approval state.
19. **Machine registry + container ID** (many containers per machine, any project).
    `~/.config/laines/registry.json` (mkdir-locked) lists `{ id, path, portRange }` for every
    container; `doctor --prune` drops entries whose path is gone. Container ID = machine-unique
    slug, default from the repo name, `--id` override. All per-lane global names are scoped by
    it: `LANE_SUFFIX=_<id>_l<N>`, Compose project `<id>-l<N>`, `LANE_ID=<id>/<lane>`. Ports: a
    machine range (default 20000–29999) is split into per-container blocks at `init` (default
    200 = 20 lanes × stride 10); lanes carve from their block; `create` still verifies ports are
    free. Range, block size, stride configurable. `config.json` keeps `ports.stride` and
    `maxLanes`; the block lives in the registry.
20. **One repo per container in v1; multi-repo lanes kept open** (option C). Data shapes are
    multi-repo-ready so option B needs no migration: `config.json` has
    `repos: { "<name>": { "remote", "defaultBranch" } }` (exactly one entry in v1, name defaults
    to the repo slug); each `lanes.json` entry has `repos: [{ "name", "path", "branch" }]` with a
    per-repo path — code never assumes the lane dir *is* the clone. v1 still clones directly
    into `lane_N/`. Future B: `lane_N/<repo>/`, one port block/env file/board entry per lane,
    safety checks per repo; open questions for B are instruction loading (lane root no longer a
    git repo), excludes, and `brief`.
21. **Board.** `.ai/context/LANES_BOARD.md`, rendered from `lanes.json` (source of truth) — state
    is never parsed back from markdown. Sections: header (container id, port block, hook policy,
    teardown mode), `## Status` (per-lane blocks between `<!-- lane:<name>:start/end -->`:
    status, branch, task, blocked on, ports + env file, 📌 kept + reason, last update),
    `## Requests` (human-action queue: teardown confirmations, hook approval/lock suggestions,
    `setup-failed` lanes, hooks exiting 3; cleared when resolved), `## Closed` (collapsed),
    `## Activity Log` (append-only, newest first, capped at 200 lines; overflow rolls to
    `.ai/archive/<date>_board-log.md`). One mkdir lock (5s wait) guards board + `lanes.json`;
    `doctor` flags a stale lock. Lane env file is `<lane>/.laines.env` (added to the lane's
    `.git/info/exclude`).
22. **Public project.** Public GitHub repo + public npm package; written for outside readers,
    no personal paths/secrets in committed files.

## Verified behavior (2026-09-28, Claude Code 2.1.284)

Throwaway fixture: container dir with `CLAUDE.md`, lane = separate git repo with committed
`CLAUDE.md` and untracked `CLAUDE.local.md`.

- Inside a lane, Claude Code loads container `CLAUDE.md` (above the lane's git root), the repo's
  `CLAUDE.md`, and `CLAUDE.local.md`.
- A plain clone outside any container loads only the repo's `CLAUDE.md`.
- Paths listed in `.git/info/exclude` (`CLAUDE.local.md`, `.ai/context/`, `.ai/plans/`,
  `.ai/README.md`, `.ai/.lane.json`) stay out of `git status`.
- Codex / Gemini not installed locally; discovery behavior researched from docs (see
  `../knowledge/build-constraints.md`).
- Permission deny rules: a container `.claude/settings.json` does **not** apply in a lane session;
  the lane's `.claude/settings.local.json` does, and stays out of `git status` via
  `.git/info/exclude`.
- MCP elicitation: supported since Claude Code 2.1.76 per docs; reaches the human even from a
  subagent's tool call. Unverified: headless `claude -p` behavior, and whether some clients
  (VS Code) auto-decline — prove with a real test server during implementation.

## Understanding (confirm or correct)

- **Stated:** standalone npm CLI bundling dot-ai; fresh containers only; per-lane local env
  isolation is the core purpose; built-in isolation primitives + hooks now, adapters later;
  agent-agnostic with Claude preferred; `data/`/`audits/` stay in the container.
- **Assumed:**
  - Node (matching dot-ai), macOS + Linux, git-only (every lane is a `git clone` of one remote)
  - existing containers are not migrated as part of this work
  - repo lives at `its own repo`
- **Success:** in an empty dir, run the installer, set a remote in `lanes.conf`, and
  `lane-create` / `lane-report` / `lane-teardown` / `watch-file` behave like the versions in
  `reference/` (including teardown's unpushed-work safety checks). Per-lane DB isolation (config
  patch, env file, DB drop on teardown) must be reproducible purely through hooks.

## What's generic vs. project-specific

| Generic (port as-is, parameterized) | Project-specific (becomes config or hook examples) |
|---|---|
| clone-per-lane, next free `lane_N` naming | repo remote URL (`LANES_REMOTE` today) |
| board + `mkdir` lock (`lane-report.sh`) | copying gitignored secrets/keys into a fresh clone |
| lane-local `.ai/` templates | per-lane DB name suffix: config patch + `skip-worktree` + env file |
| teardown: archive plans, delete context, mark closed | dropping a lane's databases on teardown |
| teardown safety: dirty tree, stashes, `rev-list --all --not --remotes` | per-lane port convention |
| `watch-file.sh` | framework-specific gotchas (seeding, test schema, shared services) |
| lane ownership rules (CLAUDE.md snippet) | |

## Approach (superseded by Decision 1 — kept for history)

`install.sh <container-dir> [--remote URL]` copies `kit/` into `<container>/.ai/`, creates
missing `.ai/` folders, writes `lanes.conf` from the example, appends the lane-ownership section
to the container's `CLAUDE.md`, and refuses to overwrite existing files without `--force`.

Rejected: plain `cp -R` with README steps (easy to miss the CLAUDE.md snippet or board
gitignore); GitHub template repo (the container itself isn't a git repo, only its lanes are).

## Design section 1: kit layout (superseded by Decision 1 — to be re-presented as a package layout)

```
laines/
├── README.md               # what it is, quickstart
├── install.sh              # copies kit/ into a container
└── kit/                    # mirrors <container>/.ai/
    ├── lanes.conf.example  # REMOTE_URL, DEFAULT_BRANCH, LANE_PREFIX=lane_, BASE_PORT
    ├── scripts/
    │   ├── lane-create.sh  lane-report.sh  lane-teardown.sh  watch-file.sh
    │   └── lib/common.sh   # config loading, paths, hook runner
    ├── hooks/
    │   └── examples/       # post-create / pre-teardown / post-teardown samples
    ├── templates/          # lane-ai-root-readme, lane-context-readme, lane-plans-readme
    ├── runbooks/lane-management.md   # generalized; project-specific gotchas stripped
    ├── context/README.md             # board-is-long-lived exception
    └── CLAUDE.snippet.md             # lane-ownership section
```

Hooks go live by copying an example from `hooks/examples/` into `.ai/hooks/`.
DB cleanup is not a generic script: it becomes a `post-teardown` hook example.

## Open decisions (from design research — see `../knowledge/build-constraints.md`)

- ~~Hooks as a human-owned boundary~~ → **decided, see Decision 11.**
- **Safety posture:** adopt the full destructive-op rules (dry-run, audit log, capabilities,
  locked mode, CLI-only `--force`) — proposed default: yes.
- **Codex/Gemini container instructions:** `laines doctor` detects and prints the per-user config
  line; L.AI.nes never edits global agent config — proposed default.
- **Config:** JSON (`.laines/config.json`) through one parse choke point, replacing shell
  `lanes.conf` — proposed default.
- **dot-ai in lanes:** lane instructions forbid `dot-ai init`/`sync`; `doctor` detects it —
  proposed default.
- **Repo hygiene:** branch flow (main-only vs. staging), whether `.ai/plans/` is tracked, and
  scrubbing this design doc of personal paths/tool references before going public.
