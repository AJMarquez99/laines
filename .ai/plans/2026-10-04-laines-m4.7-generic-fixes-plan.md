# L.AI.nes M4.7 — repo-agnostic fixes from the first adoptions (implementation plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Fix what the myapp and otherapp adoptions exposed, in ways that hold for any user's project:
no stack, version manager or repository layout is assumed. laines adapts to what the repository itself
commits, never hides a file the repository could commit, and finishes its own migrations completely.

**Sources:** `.ai/audits/2026-10-03_myapp-adoption.md` ("Follow-up … Still open" items 1–4), the otherapp
adopt dry run (2026-10-03: an adopted lane's `.laines.env` `PORT` overrides the project's own `PORT`), and the
mise migration (2026-10-04: tools launched through a version manager's exec wrapper leak its PATH into hooks).

**Principle (user, 2026-10-04):** every change is self-contained in laines — no knowledge of mise, Node,
Docker or any other user's toolchain. Where a tool-specific concern exists, laines exposes a generic
mechanism (hooks, the repository's own files) and documents the pattern with examples only.

**Tech stack:** Node ≥20 ESM, vitest, real git in tests (`test/helpers.js`).

**Spec:** `.ai/plans/2026-09-29-laines-spec.md`, `.ai/plans/2026-10-02-laines-m4.5-adopt-design.md`, M4.6 plan.

## Global Constraints

- Everything in the M1–M4.6 Global Constraints still applies: exit codes `0/1/2/3/4`, JSON by default with
  `--format table`, `--dry-run` a true no-op, commands return data and never print,
  `readJson`/`writeJson`/`writeFileAtomic` for files, every `lanes.json` change through `updateLanes`, git only
  through `deps.git`/`deps.gitAsync`, every command through the registry's `invoke`, conventional commits staged
  by explicit path.
- **Repo-agnostic:** no code path names a specific language, package manager, version manager or container
  tool. Detection is limited to git facts (what the repository tracks) and laines' own files.
- Never overwrite, delete or hide (via git excludes) a file the user may want to commit.
- Commit trailer, exactly: `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`.
- The user's shell aliases `rm`/`cp`/`mv` to interactive prompts: `command rm -f` / `command cp` / `command mv`
  in Bash, Node `fs` in tests; any shell snippet in docs that moves/copies/deletes files uses `command …`.

## Decisions (controller rulings, 2026-10-04)

- **Lane plans follow the repository.** If the repository tracks anything under `.ai/plans/` (or
  `.ai/context/`), that directory is project content in this repo: the lane exclude block does not hide it, so a
  plan written in a lane shows in `git status` and can travel in the branch. laines then excludes only the exact
  files it writes there (`/.ai/plans/README.md`, `/.ai/context/README.md`) unless those are tracked too. Lane
  rules and the brief say which case applies. Teardown's archive of *untracked* plans is unchanged.
- **An adopted lane keeps the project's own runtime settings.** The lane `adopt` creates is recorded as
  `adopted: true`; its `.laines.env` omits `PORT` (the project already runs on its own ports; laines' port block
  stays available as `LANE_PORT_BASE`/`LANE_PORT_COUNT`). `compose` (M4.6) stays as is. A pre-M4.7 lane with
  `compose` set was made by `adopt` (only adopt sets it), so `refresh` backfills `adopted: true` for it.
- **Toolchains are the project's business.** No version-manager logic in laines. Docs explain: version pins
  committed in the repository reach every lane; tools that trust per directory need a trust step per lane path
  (do it in `post-create` if your policy allows); hooks inherit laines' environment, so launching laines
  through a wrapper that rewrites `PATH` changes what hooks run.
- **Version:** bump to `0.2.0` (behaviour changed since 0.1.0: layout 2, migrations, lane state fields).

## Review Focus

1. A repository that tracks `.ai/plans/` but not `.ai/plans/README.md`: a new plan file in the lane is visible
   to `git status`; laines' README there is not.
2. A repository that tracks nothing under `.ai/`: the block is exactly as before (directories excluded).
3. A repository that starts or stops tracking `.ai/plans/` later: refresh rewrites the block, doctor agrees
   (shared function), nothing oscillates.
4. A pre-M4.7 container with stale `lane-management.md` text in its `CLAUDE.md`/`AGENTS.md`/`GEMINI.md` block
   and in its migrated `_lane-local-instructions.md`: refresh fixes both without touching user text outside
   laines' block / outside laines' own path strings.
5. An adopted lane whose project sets `PORT` itself: sourcing `.laines.env` leaves `PORT` alone; a created lane
   still gets `PORT`.

### Task 1: lane exclusions and rules follow the repository (`.ai/plans/`, `.ai/context/`)

**Files:** `src/lib/lane-files.js` (`laneExcludes`), `src/commands/doctor.js` (uses the same function — verify),

`templates/lane-ai-readme.md`, `templates/lane-plans-readme.md`, `templates/_lane-management` source
(`templates/lane-management.md`), README, spec (§7.2 / lane files). Tests: lane-files, doctor, brief, a
create/refresh test against a repo that tracks `.ai/plans/x.md`.

- `laneExcludes(deps, laneDir)`: for a directory entry (`/.ai/context/`, `/.ai/plans/`): if the repository
  tracks any path under it (one `git ls-files -z -- <dir>` call; reuse/extend `untrackedEntries`' pattern),
  replace the directory entry with the exact laines-written files in it (`/.ai/context/README.md`,
  `/.ai/plans/README.md`), each dropped if tracked. Exact-file entries keep the M4.6 rule (dropped when
  tracked). Glob entries unchanged. While there, compute tracked status with ONE `git ls-files` call for all
  entries instead of one per entry.
- Lane rules (lanes-block rule 1, lane-local instructions, lane `.ai/README.md` template, plans README template,
  runbook): reword generically — "A lane owns its `.ai/context/` and `.ai/plans/`. If the repository commits
  files under `.ai/plans/`, plans you write there are part of your branch: commit them with the work they
  describe. Otherwise they stay local and are archived when the lane is torn down." (Same idea for context only
  if the template mentions context's fate.) Keep wording tight; templates are rendered for every lane.
- `brief`: one rule line computed per lane: "This repository commits `.ai/plans/`: commit plans with your
  work." or "Plans in `.ai/plans/` stay local to this lane." (git fact via `isTracked`-style check).
- Tests: repo tracking `.ai/plans/a.md` → block has `/.ai/plans/README.md`, not `/.ai/plans/`;

### Task 2: refresh completes laines' own migrations and shows every write

**Files:** `src/commands/refresh.js`, `src/lib/container-files.js` (migration), `src/lib/agent-files.js`
(`upsertBlock`), `src/commands/init.js` (block rendering — extract a shared helper), `src/lib/format.js`,
`package.json` + `src/version.js` (0.2.0), README, spec. Tests: refresh, container-files, init.

- **Agent-file blocks:** `refresh` re-renders the container's lanes block in each configured agent file
  (`CLAUDE.md` / `AGENTS.md` / `GEMINI.md` per `config.agents`) with the current template, through the existing
  `upsertBlock` (it only replaces text between laines' markers; user text outside is untouched). Share the
  rendering with `init` (one helper). Run it in the same container-level step as the layout migration (under the
  container lock); result field `agentBlocks: [file…]` lists files whose block changed.
- **Stale paths in migrated templates:** when the migration renames a laines template/runbook to its `_` name
  (or finds an already-migrated `_` file in a container whose layout it is stamping), it rewrites only laines'
  own old path strings inside the five laines files: `runbooks/lane-management.md` → `runbooks/_lane-management.md`
  and `templates/lane-<x>.md` → `templates/_lane-<x>.md` for the four lane templates (match the path with its
  `runbooks/` / `templates/` prefix, not the bare file name, so prose about other files is untouched). Report
  them under `migrated` (or a sibling `rewritten` field). For myapp: its `_lane-local-instructions.md` still
  says `.ai/runbooks/lane-management.md` — since myapp is already at layout 2, ALSO apply this path rewrite on
  every refresh to the five `_` files (idempotent; a no-op once fixed).
- **Dry run shows every write:** `refresh --dry-run` reports, in addition to `wouldMigrate`: `envChanges`
  (keys of `.laines.env` that would be added/changed/removed, with old → new values), `excludeChanges` (entries
  added/removed), `agentBlocks` (files whose block would change), and the lane files it would write/skip. Table
  output prints them. Compute these from the same functions the real run uses (no duplicated logic).
- **Version:** `0.2.0` in `package.json` and wherever `VERSION` comes from; tests asserting the version string
  updated. (Marker `lainesVersion` keeps recording the creating version; don't rewrite it.)
- Tests: a container whose CLAUDE.md block is the pre-M4.6 text → refresh replaces the block, user text above
  and below untouched, `agentBlocks` lists it; `_lane-local-instructions.md` with the old runbook path → fixed,
  and a user sentence mentioning `lane-management.md` without the `runbooks/` prefix untouched; second refresh
  no-op; dry run reports env/exclude/block changes and writes nothing (compare file bytes before/after).

### Task 3: an adopted lane keeps the project's ports; toolchain docs

**Files:** lane-state schema (`src/lib/lanes-state.js`), `src/commands/adopt.js`, `src/lib/lane-files.js`
(`laneVars`/`laneEnv`), `src/lib/hook-events.js` (hook env goes through `laneVars`), `src/commands/refresh.js`
(backfill), `templates/lanes-block.md` rule 6, `templates/hooks-readme.md`, `templates/lane-management.md`,
README (new short section "Toolchains and version managers"), spec §8.3. Tests: adopt, lane-files, refresh,
hook-events.

- Lane state gains optional `adopted: true` (old files parse). `adopt` sets it on its lane.
- `laneVars`: for an adopted lane, omit `PORT` (all other variables unchanged, including `LANE_PORT_BASE`,
  `LANE_PORT_COUNT`, `COMPOSE_PROJECT_NAME` from `compose`). `laneEnv` adds one comment line for an adopted
  lane: `# Adopted checkout: PORT is not set, so the project's own port settings stay in effect.` Hook
  environment for an adopted lane likewise has no `PORT` from laines (if `process.env.PORT` exists it passes
  through as before — don't delete the user's own variable).
- `refresh`: a lane with `compose` set and no `adopted` → set `adopted: true` (via `updateLanes`) before
  rendering; report `backfilled: ['adopted']` (or similar) in the result.
- Lane rule 6 (lanes-block) and hooks README: say `PORT` is set for lanes laines cloned, not for an adopted
  checkout, which keeps the project's own ports.
- **Toolchain docs (no code):** README section + hooks README + runbook paragraph, generic, with examples
  labelled as examples:
  - version pins the repository commits (`.tool-versions`, `.node-version`, `.python-version`, `mise.toml`,
    `rust-toolchain.toml`, …) reach every lane, because lanes are clones;
  - tools that trust per directory (e.g. `mise trust`, `direnv allow`) need that step once per lane path —
    put it in `post-create` if the project's policy allows it;
  - install toolchains/dependencies in `post-create` (example: `mise install && npm ci`, `uv sync`), and make
    it idempotent (refresh re-runs it);
  - hooks inherit the environment laines runs with: launching laines through a wrapper that rewrites `PATH`
    (some version managers' `exec`/`x` commands do) puts that tool first for every hook; prefer a wrapper that
    invokes the runtime binary directly, or call your version manager explicitly inside the hook.
- Tests: adopt → lane state `adopted: true`, `.laines.env` has no `PORT=` line but has `LANE_PORT_BASE`;
  created lane still has `PORT`; refresh backfills `adopted` for a lane with `compose`; `laneHookVars` for an
  adopted lane has no `PORT`.
