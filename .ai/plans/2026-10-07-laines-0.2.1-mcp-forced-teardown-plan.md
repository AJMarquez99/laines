# L.AI.nes 0.2.1 — forced teardown over MCP with a typed human confirmation (implementation plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** A human already in the MCP teardown prompt can discard a lane's unpushed work without switching to a
terminal, by typing the lane's name in a second, separate confirmation. The prompt and every refusal say which of
those commits another lane of the same container also holds.

**Source:** `.ai/notes/mcp-forced-teardown.md` (from the myapp container, 2026-10-07). User: "update it as a patch
release for local versioning" → version `0.2.1`, no npm publish.

**Architecture:** a git-only lib function finds which sibling lanes hold the tips of the lane's unpushed refs; the CLI
refusal/dry run and the MCP prompt show it. The MCP teardown handler gains a second elicitation (typed lane name)
that runs the teardown with `force` — only when the sole blocker is unpushed work, the container allows it, locked
mode is off, and the checks did not change between the prompt and the run.

**Tech stack:** Node ≥20 ESM, vitest, `@modelcontextprotocol/sdk` (elicitation already used), real git in tests.

**Spec:** `.ai/plans/2026-09-29-laines-spec.md` §9.3 (teardown over MCP) and §10.3 (teardown).

## Global Constraints

- Everything in the M1–M4.7 Global Constraints still applies (exit codes, JSON/table, `--dry-run` no-op, commands
  return data, `updateLanes`, git via `deps.git`, registry `invoke`, conventional commits by explicit path, never
  stage `.superpowers/`).
- **Repo-agnostic:** git facts and laines' own files only; tool names (e.g. Docker) only as labelled examples in docs.
- **The agent can never force:** no `force` (or similar) parameter in any MCP tool schema (existing test stays green);
  only a human's typed answer unlocks it.
- Never discard more than the human was shown.
- Commit trailer, exactly: `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`.
- `command rm -f` / `command cp` / `command mv` in shell and in doc snippets.

## Decisions (controller rulings, 2026-10-07)

- New config `teardown.mcpForce: "confirm" | "off"`, **default `"confirm"`** (the human types the lane name every
  time). `"off"` keeps 0.2.0 behaviour. Settable with `laines config set` (human-only).
- **Locked mode disables the forced path** (the registry already refuses `teardown` with `force` when locked; the MCP
  handler checks locked first and simply refuses as today — no second form).
- Only unpushed work can be forced. A kept lane, a closed lane, a disabled `teardown` capability, `teardown.mcp`
  `off`/`auto`, and a client without form elicitation behave exactly as in 0.2.0.
- **Sibling holdings are informational only**: they never exempt commits from the check (two lanes holding the same
  commits torn down concurrently would otherwise each count on the other).
- Docker/service cleanup on teardown: docs only — a labelled example `pre-teardown` hook.
- Version `0.2.1`. The note graduates into this plan: delete `.ai/notes/mcp-forced-teardown.md` and its index row.

## Review Focus

1. A teardown whose unpushed work changes between the second prompt and the run (an agent commits again): refused,
   nothing touched.
2. Wrong typed name, empty answer, decline, cancel, timeout on the second form: refused, nothing touched.
3. Locked mode or `mcpForce: off`: the second form is never shown; the refusal names the terminal command.
4. A sibling lane whose clone is missing, mid-rebase, or not a repo: the holdings lookup skips it, never throws.
5. Two refs with different tips, one held by a sibling and one not: the prompt says which.

### Task 1: which sibling lanes hold the unpushed commits (git only)

**Files:** `src/lib/lane-git.js` (new `siblingHoldings`), `src/commands/teardown.js` (refusal text + dry-run result),
`src/lib/format.js` (teardown table), README (teardown row), spec §10.3. Tests: `test/lane-git.test.js` (or the
existing unpushed-work test file), `test/teardown.test.js`.

- `siblingHoldings(deps, ctx, laneName, refs)` → for each unpushed ref `{ ref, commits }` (from `unpushedWork`):
  resolve its tip (`git rev-parse <ref>` in the lane), then for each OTHER lane of the container whose state is not
  `closed` and whose clone exists and has `.git`: if `git -C <other> cat-file -e <tip>^{commit}` succeeds, list
  `git -C <other> for-each-ref --contains <tip> --format=%(refname) refs/heads refs/tags` (local branches and tags
  only; a reflog or remote-tracking ref is not "held"). Return
  `[{ ref, commits, heldBy: [{ lane, refs: [...] }] }]`. Any git failure for one sibling skips that sibling
  (never throws). Pure read.
- Teardown (`--remove-dir` with unpushed commits): `checks.holdings` carries the result (dry run and refusal); the
  refusal text adds one line per ref: `  - <ref> (<n> commits): also in lane_1 (refs/heads/x)` or
  `… : held by no other lane`. Table output prints the same.
- Tests (real git, two lanes of one container via the existing helpers): lane_2 has 2 unpushed commits that lane_1
  also has on a branch → holdings name lane_1; a second unpushed ref only in lane_2 → `heldBy: []`; a closed sibling
  and a sibling with a deleted clone are skipped; refusal text contains both lines; dry run result has
  `checks.holdings`.

### Task 2: forced teardown over MCP with a typed confirmation; config; docs; version

**Files:** `src/mcp/teardown.js`, `src/config.js` (`teardown.mcpForce`), `src/commands/config.js` if keys are
whitelisted, `src/commands/teardown.js` (accept an `expect` fingerprint — see below — and record how it was forced),
`src/lib/audit.js` usage, README (teardown over MCP table + config), `templates/hooks-readme.md` (example
`pre-teardown`), `templates/lane-management.md`, spec §9.3/§6.1, `package.json` + lock (`0.2.1`),
`.ai/notes/` (delete the note + index row), roadmap row. Tests: `test/mcp.test.js` (SDK in-memory client with
elicitation), `test/teardown.test.js`, `test/config.test.js`.

- Flow in `runTeardownMcp` when `teardown.mcp` is `confirm`:
  1. Dry run as today. If `plan.blocked` (only unpushed work sets it) AND `mcpForce === 'confirm'` AND not locked AND
     `deps.canElicit()`: continue below; otherwise behave exactly as 0.2.0 (throw `plan.refusal`).
  2. First form: today's confirmation, with "Unpushed work" listing each ref, its commit count and the sibling
     holdings, plus "you'll be asked to type the lane name to discard it".
  3. Second form: message = exactly what will be lost (each ref, its count and up to 3 commit subjects via
     `git log --format=%s -n 3 <tip> --not --remotes`; dirty files (first 10 + "and N more"); stash count) and the
     holdings; schema `{ lane: { type: 'string', title: 'Type <lane> to discard this work' } }`, required.
     Accept only `action === 'accept'` and `content.lane.trim() === <lane>`; anything else → `BlockedError` "Not
     confirmed: nothing was torn down." (and for a wrong name, say the name didn't match).
  4. Run `invoke('teardown', { ...args, force: true, expect: <fingerprint> }, deps)`. `runTeardown` with `expect`
     recomputes the checks and refuses (`BlockedError`, nothing touched) if the fingerprint differs — fingerprint =
     stable JSON of `{ refs: [{ref, tip}], dirty: [...sorted], stashes }`. The CLI never passes `expect`.
  5. Audit `teardown` entry gains `forcedVia: "mcp-typed-confirmation"` and `discarded: checks.problems`; the board
     activity line says "torn down over MCP; forced after a typed confirmation: <problems summary>".
- `teardown.mcpForce` in the config schema (`confirm` | `off`, default `confirm`), documented in README/spec, settable
  via `laines config set teardown.mcpForce off`.
- Docs: README "Teardown over MCP" table gains the forced path and its limits; hooks README + runbook get a labelled
  example `pre-teardown` that stops a lane's services while the clone still exists, e.g.
  `docker compose -p "$COMPOSE_PROJECT_NAME" down -v` ("example — use your project's own stop command").
- Version `0.2.1` (package.json + package-lock.json; tests asserting the version).
- Tests (MCP in-memory client with a scripted elicitation responder): blocked lane + first accept + typed correct name
  → clone removed, `forced: true`, audit `forcedVia`; wrong name → refused, clone intact; decline on the first form →
  refused; decline/cancel on the second → refused; elicit throws (timeout) on the second → refused; `mcpForce: off`
  → refusal text, no second form (responder asserts it was asked once); locked → same; kept lane → kept refusal; a new
  commit made in the lane between the second form and the run (do it inside the responder) → refused by the
  fingerprint, clone intact; client without elicitation → board request as 0.2.0; tool schemas still declare no
  `force`.
