## Decision needed from the user — fix 1 vs. the 0.4.8 closed-lane exclusion (`de1473e`)

The note asks to offer the typed force form for a closed lane's leftover clone. That reverses a 0.4.8 rule, so here is
why the exclusion exists, for the user to decide:

1. **The 0.4.8 ruling grouped "closed" with "kept"** ("a closed lane behaves exactly as in 0.2.0"). That was a
   conservative default, not a principled argument: unlike a kept lane, a closed lane has no human pin on it.
2. **A real technical gap (the reason `de1473e` landed):** the closed-lane teardown path runs no `pre-teardown` hook,
   so it skipped the second, under-lock fingerprint re-check that 0.4.8 added. That's fixable: re-check immediately
   before `removeLaneDir` on that path too.
3. **A substantive risk the note itself shows:** a closed lane's clone is *unowned* — no board entry tracks it, so
   work done there after closing (myapp's multi-commit feature branch) is the easiest work to lose by
   accident. The typed form would list it, but it doesn't currently say "created after the lane closed".

**Options:**
- **A (recommended): lift the exclusion with safeguards** — offer the typed form for a closed lane whose clone exists
  and is a git repo; add the fingerprint re-check right before `removeLaneDir` on the closed path; mark every ref whose
  tip is newer than the close as "changed after the lane closed" in both forms; keep sibling holdings. Spec §9.3
  records the reasoning.
- **B: keep the exclusion** — closed lanes stay terminal-only for forced removal; write the reason (points 2–3) into
  spec §9.3; fixes 2–5 still ship.

**User decision (2026-10-11): option A.** Task 3 below implements it.

## Review Focus

1. A closed lane whose clone gained a branch after closing: doctor fails the check and names the refs; the typed form
   (option A) labels them "after the lane closed".
2. Fix 2's checkbox ticked on a lane with unpushed work: the flow continues into the typed form (or refuses with
   nothing touched) — never a half-teardown that closes the lane but keeps the clone silently.
3. `create` with lanes 1 and 3 open, lane_2 closed with its clone present → picks `lane_4`, not `lane_2`; an explicit

4. A `laines-mcp` started before an upgrade: `laines_status`/`laines_doctor` say it's stale; a refusal from it says so
   too; a fresh server says nothing.
5. Closed lane, clone deleted by hand: doctor is quiet (nothing left to flag).

### Task 1: `create` skips numbers whose directory is a leftover (fix 4)

### Task 2: doctor flags closed lanes whose clone remains (fix 3)

**Files:** `src/commands/doctor.js`, `src/lib/lane-git.js` (a small read-only helper), `src/lib/format.js`, README
(doctor row), spec §5. Tests: `test/doctor.test.js`.

- New check per closed lane whose clone still exists: `closed:<lane>`.
  - Clone exists, no ref tip newer than `lane.closed`: **ok with a note** — "closed, but its clone remains: delete it
    with `laines teardown <lane> --remove-dir`, or ignore".
  - A ref (`refs/heads`, `refs/tags`) whose tip's committer date is after `lane.closed`, or uncommitted changes: **fail**
    — "closed on <date>, but its clone has N ref(s) changed since (<ref> …) and <dirty> uncommitted file(s): this work
    belongs to no open lane — push it or move it to a lane, then delete the clone".
  - A closed lane whose clone is gone: no check (quiet). A closed lane with no `closed` timestamp (old state): note
    only.
- Committer dates are a heuristic (rewritable), which is fine for a doctor finding; documented.
- Tests: closed + clean clone → ok + note; closed + new branch committed after the close → fail naming the branch;
  closed + dirty → fail; closed + clone deleted → no check; table output shows the note with `•`.

### Task 3: MCP teardown — "also delete the clone" choice, and typed force for a closed lane's clone (fixes 2 and 1)

**Files:** `src/mcp/teardown.js`, `src/commands/teardown.js`, `src/lib/lane-git.js` (reuse Task 2's "changed since

- Under **option B**: skip the `canForce` change; spec §9.3 gains the reasoning; fix 2 unchanged.
- Tests: tick "also delete" on a clean lane → closed and removed in one confirmation; tick it on a lane with unpushed

### Task 4: show a stale `laines-mcp` (fix 5)

**Files:** `src/mcp/server.js`, `src/version.js` (a fresh read of the installed version), `src/commands/doctor.js`,
the status command, `src/mcp/tools.js` (error wrapping), README (MCP section), spec §9 (MCP). Tests: `test/mcp.test.js`,
`test/doctor.test.js`.

- The server records the version it started with (`VERSION` at import). On each call it re-reads the installed
  version from its own `package.json` on disk (no network, no tool assumptions). When they differ:
  - `laines_status` and `laines_doctor` results include `server: { running, installed, stale: true }`, and doctor adds
    a failing `mcp-server` check: "this laines-mcp is running <running>, but <installed> is installed: reconnect
    laines in your MCP client (for example /mcp in Claude Code)";
  - every refusal/error a tool returns gets one appended line with the same message, so a stale server explains
    itself exactly where it would otherwise look broken.
- A CLI `laines doctor` (no server) reports nothing new.
- Tests: in-memory server whose recorded version differs from the one on disk (inject both via deps) → status/doctor
  carry `stale: true`, a refusal carries the line; equal versions → nothing added.

### Decision needed — hooks on a closed lane's later clone removal

Today the closed-lane `--remove-dir` path runs **no** `pre-teardown` (`runPre = !closed`) and runs `post-teardown` only
to retry a failed one (`runPost = !closed || cleanupPending`) — myapp's audit shows `hooks: { pre: null, post: null }`.
`pre-teardown` already ran once, at the close, while the clone existed — so a cleanup hook (like 0.4.8's example that
stops the lane's services) normally does its job then. But a clone **reused after closing** (myapp started services
again from it) is deleted with no hook, leaving whatever it started running. This also matters to option A: the
typed-force path for a closed lane removes such a clone with no project cleanup.

- **Option H1 (recommended): run `pre-teardown` again on a closed lane's clone removal when the clone exists** (same
  policy/approval/timeout as a first teardown; `LAINES_HOOK=pre-teardown`, plus a new `LAINES_TEARDOWN_PHASE=remove-clone`
  so a hook can tell the two apart). A failure aborts the removal with nothing touched, as today for a first teardown.
  On the forced MCP path, the existing under-lock fingerprint re-check then runs after this hook (as it does for open
  lanes), so a hook that changes the clone gets the removal refused. Docs: the example hook must be safe to run twice.
- **Option H2: keep no hooks there**, and document it: README/hooks README/runbook say the cleanup hook runs at close
  only; a clone reused after closing must be cleaned up by hand before `--remove-dir`.

### Task 7 (user direction, 2026-10-11): tearing down a lane deletes it unless told otherwise — DRAFT, details awaiting approval

**User:** "When we teardown a lane or close a lane that should signify deleting the lane itself unless specified

- **Default flips:** `laines teardown <lane>` and `laines_teardown` delete the clone by default (after the same

- **Closed lanes with a clone** become the explicit-keep case only; Task 6 (record + board line) and the doctor
  `closed:<lane>` check still cover them.
- **Safety unchanged:** kept lanes refused; unpushed work never deleted without `--force` (CLI) or the typed name (MCP);
  `pre-teardown` runs before anything is touched; dry run shows that the clone will be deleted.
- Docs: README, spec §5/§9.3/§10.3, runbook, hooks README, lane rules mention of teardown; tests updated for the new
  default (most teardown tests pass `--remove-dir` today — keep a set that exercises the default and `--keep-dir`).
