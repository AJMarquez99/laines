# L.AI.nes 0.4.11 — hook trust model (implementation plan)

**Status:** APPROVED by the user on 2026-10-16 (items 1, 2 and 3).
**Source:** pre-public security review, finding F2. Agents may write `.laines/hooks/*` (lane rule 5)
and may trigger `create`/`refresh`; under the default `notify` policy a new or changed hook runs at
once. A hook could call a human-only laines command (`teardown`, `config set`, `hooks policy` …) and
so step around the MCP confirmation gates that 0.4.8/0.4.9 built for agentic management.

**Framing (must be stated in code comments and docs):** a hook is arbitrary code running as the
user. It can `unset LAINES_HOOK`, edit `.laines/config.json` directly, or skip laines entirely. Nothing
in laines can stop that. The real boundary is the hook policy (`approve` keeps agent-written hooks
from running until a human approves them). Item 2 is a guardrail against accidents, not a control.

## 1. Trust model in the README

- New `## Trust model` section (after `## Isolation model`, before `## Toolchains…`), short:
  - Hooks run as you, outside your agent's permission prompts. Under `notify` (default) a hook that
    anyone (you, an agent, a script) writes to `.laines/hooks/` runs on the next `create`/`refresh`;
    the board note and `laines doctor` are how you notice. Use `laines hooks policy approve` when
    agents or untrusted content could write hooks.
  - The Claude deny rules steer agents onto the MCP tools, where `teardown.mcp` / `teardown.mcpForce`
    decide when a human confirms. They are prefix rules: a determined agent can get around them
    (e.g. `sh -c`). They are a guardrail, not a sandbox.
  - `hooks.manage` (item 2) and its limits.
  - Repositories: laines never executes anything a repository commits; a lane refuses symlinks
    committed at `.ai`, `.ai/context`, `.ai/plans`, `.claude` or at any file laines writes (0.4.10).
- Soften the `## What init sets up` deny-rules bullet: "so agents are steered to the MCP tools
  instead of running human-only commands … from a shell (a guardrail; see Trust model)".
- Lane rule 5 in `templates/lanes-block.md`: add that hooks must not call laines' human-only
  commands (they are refused unless a human enables `hooks.manage`). Keep wording terse.

## 2. Guard + `hooks.manage` setting

- `src/config.js`: `hooks.manage: z.boolean().default(false)`.
- `src/commands/registry.js`:
  - Entries gain `gate: true` for `config set`, `hooks approve`, `hooks policy` (they change the
    gates themselves). `adopt` is also always refused from a hook (it makes a new container; there
    is no container config to consult).
  - In `invoke`, before anything else: if `entry.humanOnly && deps.env.LAINES_HOOK`:
    - gate commands and `adopt` → `BlockedError` always;
    - `teardown`, `release` → `BlockedError` unless the container config has `hooks.manage: true`.
    - Message names the hook event (`LAINES_HOOK` value), the command, and how a human enables it
      (`laines config set hooks.manage true`) — for gate commands, say it is never allowed.
    - Comment: guardrail only; a hook can unset the variable; the hook policy is the boundary.
  - Make sure `deps.env` is what's consulted (tests inject env); check the CLI and MCP both pass deps
    with `env`.
- `hooks.manage` is set with `config set` (human-only, refused from a hook, refused under `locked`).
- Audit: append an audit line when a hook-originated human-only command is refused
  (`action: 'hook-refused'`, command, event) if `appendAudit` is reachable cheaply; otherwise skip.
- Tests (`test/registry.test.js` or a new `test/hook-guard.test.js`):
  - with `LAINES_HOOK` set: `teardown`/`release` refused by default; allowed with `hooks.manage`;
    `config set`, `hooks approve`, `hooks policy`, `adopt` refused even with `hooks.manage`;
  - without `LAINES_HOOK`: unchanged behaviour;
  - non-humanOnly commands (`report`, `create`) unaffected with `LAINES_HOOK` set;
  - end-to-end: a real `post-create` hook that runs `laines release lane_1` (via `process.execPath
    bin/laines.js`) fails and the lane stays kept/whatever state; with `hooks.manage` it succeeds.
    (Skip if hook e2e infra makes this heavy; the unit tests are required.)

## 3. `doctor` flags unapproved hooks under `notify` / `open`

- In the `hooks` check (`src/commands/doctor.js` ~190): when policy is not `approve` and any hook is
  `new` or `changed`, surface it as a warning: "`X` (new|changed) will run unapproved on the next
  create/refresh: review with `laines hooks status`, then `laines hooks approve`". Use doctor's
  existing warning level if it has one; if it only has pass/fail, add it as a clearly worded note in
  the passing line (do not make `doctor` fail for the default policy). Under `open`, word it as
  "runs without approval by policy".
- Test in `test/doctor.test.js`.
