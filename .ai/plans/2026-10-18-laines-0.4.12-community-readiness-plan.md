# L.AI.nes 0.4.12: community readiness (implementation plan)

**Status:** APPROVED by the user on 2026-10-28, after a Fable review (verdict "ready after fixes").
**Shape (user, 2026-10-28):** do everything possible while the repo is private (Phase A, released as
0.4.12), make it public, then do the settings that GitHub only offers on public repos as
fast-follows (Phase B).
**Out of scope:** npm publishing, the pack round-trip test and the pre-release agent checks. These
stay in M5 proper.
**Source:** a comparison with the family's public repos (discord-cli, gmail-cli, dot-ai) on
2026-10-16.
**Base:** `main` at `bbe77d2` (0.4.11).

## Goals

1. Anyone who finds the repo knows how to report a vulnerability privately, how to contribute, and
   what laines does and does not protect against.
2. Every push and PR runs lint, audit and tests on macOS and Linux.
3. Once public, `main` can't be force-pushed or deleted, and only takes changes that passed CI.
4. Avoid the gap found in the siblings, where the docs pointed to private vulnerability reporting
   while it was switched off.
   - Private vulnerability reporting can only be enabled on a public repo.
   - So turn it on in the same sitting as the flip (§B1).
   - Until then, `SECURITY.md` also gives the email address.

## Why two phases

On the free plan, a **private** repo can't have:
- rulesets: `gh api repos/AJMarquez99/laines/rulesets` returns 403 "Upgrade to GitHub Pro or make
  this repository public";
- private vulnerability reporting (404);
- secret scanning or push protection (`security_and_analysis` is `null`).

Dependabot alerts and security updates *do* work while private. So 0.4.12 is the last release that
reaches `main` by fast-forward.

## Non-goals

- `release.yml`, npm Trusted Publisher, and the first npm publish (M5 proper).
- `npm pack` round-trip test, pre-release agent checks (M5 proper).
- `CHANGELOG.md` and `install.sh`: only some siblings have them; the roadmap tables are the change
  history.

## A1. Community files (match the siblings' structure and voice)

Model each file on discord-cli's version, then rewrite its contents for laines. Don't copy text
that doesn't apply.

### `SECURITY.md`

**Supported versions:** the latest release only. Until laines is on npm, that means the latest `v*`
tag.

**Reporting:**
- Use the private Security tab ("Report a vulnerability"), which is enabled when the repo goes public
  (§B1), or email `alejandromarquez@live.com`.
- Do not open a public issue.
- Reports are acknowledged within a few days.

**What laines protects and what it doesn't:** a short threat model. Link the README's
`## Trust model` section rather than repeating it.
- Hooks run as the user.
  - The hook policy is the boundary: `approve` keeps new or changed hooks from running until a
    human approves them.
  - `hooks.manage`, the `LAINES_HOOK` refusal, and the Claude deny rules are guardrails, not a
    sandbox.
- **laines itself** never executes anything a repository commits.
  - A hook the user wrote, such as `post-create` running `npm ci`, may execute repository
    content. That is the user's choice.
  - A lane refuses symlinks at `.ai`, `.ai/context`, `.ai/plans`, `.claude`, and at any file
    laines writes.
- **By default**, teardown over MCP needs a human to confirm:
  - `teardown.mcp: confirm` and `teardown.mcpForce` with a typed confirmation;
  - a client that can't elicit is refused outright (`src/mcp/teardown.js:136`);
  - with `teardown.mcp: auto`, the CLI's checks apply with no human prompt
    (`src/mcp/teardown.js:95-102`).
- Locked mode and capabilities limit what `laines-mcp` may do (`src/commands/registry.js:72-83`).

**In scope for reports:**
- deleting or writing outside a lane or container;
- teardown deleting a clone with unpushed, uncommitted or stashed work, or a kept lane, without
  `--force` or the typed MCP confirmation (`src/commands/teardown.js`: unpushedWork,
  forceFingerprint, the `expect` re-check);
- an agent getting past a confirmation gate without running a hook;
- `laines-mcp` performing a locked-refused or capability-denied action without
  `.laines/config.json` being edited;
- laines itself executing committed repository content;
- writing through a committed symlink.

**Out of scope (documented trust model):**
- anything a hook does, including hooks running under `notify` or `open` policy;
- a hook unsetting `LAINES_HOOK` or editing `.laines/config.json`;
- agents getting around the Claude deny rules (e.g. `sh -c`), since those are prefix guardrails;
- code the user runs themselves;
- other local users reading the board or audit log. These are plain files under the user's umask,
  and laines makes no file-mode guarantee.

**Hygiene:** never paste `.laines/` audit logs, board contents or paths that name private repos
into an issue.

### `CONTRIBUTING.md`

- **Setup:** clone, `npm install`, Node ≥ 20, `npm run test:run`, `npm run lint`.
- **Test rules:**
  - Tests use temporary directories and local bare repos only.
  - They never touch the user's real containers, the machine index (`LAINES_CONFIG_DIR`, under
    `~/.config` by default; `test/helpers.js:27-28` redirects it), or the network.
- **Code rules:**
  - CLI and `laines-mcp` share one registry and gated layer, so keep both paths consistent.
  - Keep safe defaults as they are: `notify` policy, `hooks.manage` false, MCP teardown gates,
    symlink refusal.
  - Update the README and the spec when a command, flag or config key changes.
- **Audit gate policy:** see §A0.
- **PR steps:** branch from `staging` and open the PR to `staging`. `main` is release-only.
- **Licence:** an MIT and Code of Conduct note.

### Other files

- **`CODE_OF_CONDUCT.md`:** Contributor Covenant 2.1, verbatim from discord-cli (contact
  `alejandromarquez@live.com`).
- **`.github/PULL_REQUEST_TEMPLATE.md`:**

## A2. CI workflows

Follow the siblings' conventions:
- `permissions: contents: read`;
- a concurrency group per ref with `cancel-in-progress`;
- actions pinned to a commit SHA with a version comment, using discord-cli's pins (checkout
  `df4cb1c…` v6.0.3, setup-node `48b55a0…` v6.4.0);
- triggers on push and PR to `main` and `staging`, plus `workflow_dispatch` for manual runs;
- `timeout-minutes: 15` on every job, because hook-runner tests spawn `sleep 30` process groups and
  a wedged child would otherwise hold a runner for 6 h.

**`.github/workflows/lint.yml`**
- The job id is exactly `quality`, with no job-level `name:`, because the ruleset requires that
  context.
- Steps on Node 22, ubuntu: `npm ci`, `npm run lint`, `npm audit --audit-level=moderate`.
- The audit step is laines' addition; the M5 roadmap asks for "lint + audit".

**`.github/workflows/tests.yml`**
- Matrix: `os: [ubuntu-latest, macos-latest]` × `node: [20, 22, 24]`, `fail-fast: false`.
- Steps: `npm ci`, `npm run test:run`.
- **No git-identity step.** `test/setup.js` sets `GIT_CONFIG_GLOBAL=/dev/null` and
  `GIT_CONFIG_NOSYSTEM=1`, every committing test sets its own identity, and `src/` never commits.
  (First CI run: two pre-teardown hook fixtures did not; fixed in the tests, not with a CI step.)
- An aggregator job `ci` (`needs: [test]`) gives the single required status check.

**Platform notes (verified by review):**
- No opener exists. The 19 `'open'` hits are the hooks `policy` enum.
- `test/helpers.js:18` realpaths tmpdir.
- The case-insensitive symlink test probes the file system at runtime, so it skips on ext4
  legitimately.
- Hooks are `#!/bin/sh`, and the process-group kills work on Linux.

The first **macOS** runner run is the likeliest place for timing failures (`hook-runner.test.js:62,85`
time budgets). Fix any failure in the code or the test, for example by widening a budget with a
reason. Never skip a test to get green.
