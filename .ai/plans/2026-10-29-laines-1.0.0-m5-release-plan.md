# L.AI.nes M5: release 1.0.0 (implementation plan)

**Status:** APPROVED (user, 2026-10-30; decisions D1–D10 below). Revised after a Fable review ("ready after fixes", 2026-10-29).
**Ends in:** `@ajmarquez99/laines` 1.0.0, the first npm release, published from CI with provenance.
**Base:** `staging` = `main` = `d45d659` (0.4.13). The repo has been public since 2026-10-29;
`main-protection`, `staging-protection` and `tag-protection` are active.
**Inputs:** roadmap M5 row; spec §12–§15; `notes/m1-deferred-findings.md`,
`notes/m2-carry-overs.md`, `notes/install-after-npm-publish.md`; the archived 0.4.12 plan
(`../archive/2026-10-29_2026-10-18-laines-0.4.12-community-readiness-plan.md`), whose Non-goals are
this plan's scope; the release workflows and runbooks of discord-cli and gmail-cli (read only).

## Goals

1. A `v*` tag on `main` publishes to npm from CI, with OIDC and provenance and no long-lived token.
2. CI proves that the packed tarball installs and works: both bins, `init`, `create`, `doctor`, and
   an MCP handshake.
3. The agent behaviour the spec leaves to manual checks (§13 last row, §15) is checked against real
   clients and recorded in an audit.
4. `SECURITY.md` states the residual risks. Every carried-over finding is either fixed, documented
   or explicitly deferred.
5. 1.0.0 states what it promises: a written compatibility policy, a supported Node range, and a
   changelog from 1.0.0 on.

## Non-goals

- New commands or features. 1.0.0 is 0.4.13 plus the fixes in §5, a raised Node floor and docs.
- Windows, or several repositories in one lane (out of scope for v1, as the README says).
- `install.sh`. The siblings that have one predate npm publishing; `npm i -g` and `npx` cover it.
- A JS API. laines ships two bins and nothing to `import` (see Decision D5).

## What the siblings did (findings, 2026-10-29)

- **First publish was manual, from a laptop.** discord-cli 0.3.0 (2026-06-14) and gmail-cli 0.7.0
  (2026-06-13) were published with `npm publish` from a local checkout. Neither version has a
  provenance attestation, and neither has a git tag. The Trusted Publisher was configured on the
  existing package afterwards (both commits named "ci: publish to npm via OIDC trusted publishing",
  2026-06-16). Provenance starts at 0.3.1 and 0.7.1.
- **npm still requires the package to exist** before a Trusted Publisher can be added
  (`npm help trust`, npm 11.19: "Package must exist"). So laines can't configure OIDC first and
  then publish 1.0.0 through it. §1.4 handles this.
- `npm trust github` (npm ≥ 11.15) now does from the CLI what the siblings did on the website.
- **A Trusted Publisher configuration expires** if no publish succeeds through it within 2 days
  of its creation (npm docs, "Trusted publisher configuration expiry"). So in every path below,
  creating it (step A6) is paired with an OIDC publish inside 48 hours.
- **npm has scheduled direct publishing with granular tokens for removal in January 2027.** Path A
  works today, but not for long; it is a one-off bootstrap, not a fallback to keep.
- Their `release.yml` runs `npm install -g npm@latest` inside the publish job, has no tag/version
  check, and gmail-cli's is not SHA-pinned. laines doesn't copy those three things.

## 1. Release pipeline

### 1.1 `.github/workflows/release.yml`

- Trigger: `push: tags: ['v*']`. Name the file exactly `release.yml`, because the Trusted Publisher
  is keyed to the filename.
- Workflow-level `permissions: contents: read`. The job adds `id-token: write`.
- `concurrency: release-${{ github.ref }}`, `cancel-in-progress: false` (never cancel a publish
  part-way).
- One job, `publish`: `ubuntu-latest` (OIDC needs a GitHub-hosted runner), `timeout-minutes: 20`,
  `environment: npm` (Decision D3).
- Steps:
  1. `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`.
  2. `actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0`, Node 24,
     `registry-url: https://registry.npmjs.org`. **No `cache:`**, so a publish job never restores a
     cache another workflow wrote.
  3. **Tag matches version:** fail unless `$GITHUB_REF_NAME` equals
     `v$(node -p "require('./package.json').version")`.
  4. **Tag is on `main`:** `git fetch --no-tags origin main`, then
     `git merge-base --is-ancestor HEAD origin/main`, else fail. Use `HEAD` after checkout, not
     `$GITHUB_SHA`: on an annotated-tag push that is the tag object, not the commit
     (actions/checkout#290). Fetch `main` explicitly rather than relying on `fetch-depth: 0`. A tag
     pushed on a branch commit never publishes.
  5. **npm is new enough:** fail unless `npm --version` is ≥ 11.5.1 (OIDC). Node 24's bundled npm
     meets this. If it ever doesn't, install an **exact** pinned version (`npm@11.x.y`), never
     `npm@latest`.
  6. `npm ci`, `npm run lint`, `npm audit --omit=dev --audit-level=moderate`, `npm run test:run`,
     `npm run test:pack` (§2).
  7. `npm publish --provenance --access public`. `prepublishOnly` runs vitest once more. That
     duplicate is accepted on purpose, because it also guards the manual fallback.
- Header comment like the siblings': how the trust is wired, that it is keyed to the filename, and
  a pointer to the runbook. No account names beyond the public `AJMarquez99/laines`.

**Acceptance:**
- `actionlint` is clean, and both actions are pinned to the SHAs above with version comments.
- Never push a test tag: `tag-protection` makes it permanent, and the workflow would try to
  publish it. Instead, run the guard steps' shell locally: the tag check fails for `v9.9.9` and
  passes for `v$(version)`, and the ancestor check fails for a commit that isn't on `main`.
- The first real run is the 1.0.0 publish (§8). Its log shows "Signed provenance statement" and
  "Published".

### 1.2 Ruleset impact

- None. The required checks stay `quality` and `ci`, and `release.yml` isn't a required check.
- `tag-protection` blocks updating and deleting `v*` tags, not creating them. So **a pushed tag is
  final**:
  - if the publish fails for an npm-side reason (Trusted Publisher mismatch, 403), fix the npm
    side and **re-run the failed job** on the same tag;
  - if the code or the lockfile must change, release 1.0.1. Never try to move the tag.
- **If `v1.0.0` is pushed but never publishes** and the fix needs a code change:
  - the CHANGELOG marks 1.0.0 "tagged, never published";
  - `v1.0.0` gets no GitHub release;
  - 1.0.1 becomes the first npm version, and the compatibility promise starts there.

## 2. `npm pack` round-trip test

**Choice: a standalone Node script run as `npm run test:pack`, not a vitest test.** Spec §13
already names it `test:pack` in CI. Reasons:
- **It's the release gate for the artifact itself.** `release.yml` runs it on the exact tree it is
  about to publish, as its own step. After publishing, the same script re-runs against the registry
  copy (`--from <spec>`). A vitest file can't take that argument cleanly.
- **The vitest suite stays hermetic.** CONTRIBUTING promises tests never touch the network. Installing
  a tarball needs registry reads for its dependencies, unless the cache already has them. Keeping
  this out of `npm run test:run` keeps that promise, and keeps `prepublishOnly` fast.
- **Cost.** Pack plus install takes about 20–60 s. Running it once per OS is enough; it doesn't
  need all 6 matrix cells.
- **Independence.** It drives the installed copy only through its bins, from outside, so nothing
  from the repo's `node_modules` or `src/` can mask a packaging bug.

**File:** `test/pack-roundtrip.mjs`. vitest's `include` (`test/**/*.test.js`) doesn't pick it up,
but ESLint does. Script: `"test:pack": "node test/pack-roundtrip.mjs"`.

**Sandbox (all under one `mkdtemp`, removed in `finally`):**
- `HOME`, `XDG_CONFIG_HOME` and `LAINES_CONFIG_DIR` point into the temp dir, so the real
  containers and machine index can't be touched.
- `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, and a fixed git identity through
  `GIT_AUTHOR_*`/`GIT_COMMITTER_*`.
- `npm_config_userconfig` is an empty temp file, so no user `.npmrc` (or token) is read.
  `npm_config_cache` is set to the real cache path, taken from one `npm config get cache` run at
  start, before `HOME` is overridden, so a warm cache still serves the install.
- The script imports nothing by package name. It runs the installed bins only (see D5).
- The remote is a local bare repo (`file://`), seeded with one commit. No network git.

**Steps and expected results:**
1. Unless `--from` is given: `npm pack --json --pack-destination <tmp>`. The file list contains
   both bins and every `templates/*` file, and nothing under `test/`, `.ai/` or `.github/`.
2. `npm install -g --prefix <tmp>/prefix <tarball|--from spec> --prefer-offline --no-audit
   --no-fund --ignore-scripts`. Try `--offline` first. After `npm ci` the cache usually lacks
   packuments, so expect ENOTCACHED, and fall back to `--prefer-offline` (registry GETs only).
3. `<prefix>/bin/laines --version` prints `package.json`'s version. Both bins exist and are
   executable.
4. `laines init <tmp>/c --remote <bare> --agents claude` exits 0. This runs the bundled dot-ai from
   the installed copy's own dependencies.
5. `laines doctor --container <tmp>/c` exits 0, and every check in the JSON is `ok`. Warnings
   and notes are allowed.
6. `laines create --container <tmp>/c`, twice: two lanes with distinct ports and env files (spec
   §14 criteria 1, 2 and 7). Port probing binds local sockets only.
7. **MCP handshake:** spawn `<prefix>/bin/laines-mcp --container <tmp>/c` and send JSON-RPC
   `initialize` over stdin.
   - The result's `serverInfo.version` equals the package version.
   - Send `notifications/initialized`, then `tools/list`. The tools include `laines_create` and
     `laines_teardown`, and exclude every human-only command (`release`, `hooks approve`,
     `hooks policy`, `config set`, `adopt`).
   - Close stdin and assert the process exits within 5 s. `bin/laines-mcp.js` has no stdin-end
     handling of its own, so this is a real check. On timeout, send SIGTERM and fail with "did not
     exit on stdin close", rather than hang the job.
8. `laines teardown <second lane> --container <tmp>/c` exits 0, and the clone is gone. The lane's branch
   is fresh from `main` and tracks it, so the unpushed-work checks pass without `--force`.
9. On any failure, print the failing step, its stderr, and the sandbox path (kept with `--keep`),
   then exit 1.

**CI:** a new job `pack` in `tests.yml`, on `[ubuntu-latest, macos-latest]` with Node 22 (the
floor line; see D1), `timeout-minutes: 15`. Node 22 bundles npm 10.9.x, so the script uses only
npm 10 features (`pack --json`, `install -g --prefix`), nothing from the OIDC-era npm 11. The aggregator becomes `needs: [test, pack]`, so the
required check is still `ci` and the rulesets don't change.

**Acceptance:**
- `npm run test:pack` passes locally and in both `pack` cells.
- The real machine index is untouched: compare `ls -la` of the default config dir
  (`$XDG_CONFIG_HOME/laines`, else `~/.config/laines`) before and after the run.
- A deliberately broken `files` entry (dropping `templates/` locally) makes step 1 or 4 fail.
  Revert afterwards.
- `npm pack --dry-run` still lists 63 files.

## 4. `SECURITY.md`: supported versions and residual risks

- **Supported versions:** "the latest 1.x release on npm". Remove the "until laines is published"
  sentence.
- **New section `## Known limitations and residual risks`**, after "Out of scope". Each item is a
  short bullet saying what happens and what to do about it.

| Item (source) | Triage | Reason |
|---|---|---|
| SSH passphrase / host-key prompts aren't covered by `GIT_TERMINAL_PROMPT=0` (m2) | **Document** | Outside laines' control. A terminal user can answer; over MCP, an agent needs an SSH agent or an unencrypted key. |
| The unpushed-work check is local, with no fetch: a stale remote-tracking ref reads as pushed (m2) | **Document** | A fetch would add network access and SSH prompts to teardown. Advise `git fetch --prune` before tearing down old lanes. |
| Ignored files (`.env`, local DBs), submodule commits and linked worktrees are outside the unpushed-work check (m2) | **Document** | By design: teardown deletes the clone. Name `pre-teardown` as the place to save them. |
| `--keep-dir` teardown still deletes `.ai/context/` (m2; spec §10.3 step 5) | **Document**, and fix the spec wording narrowly | The behaviour is intended. What §10.3 says about the clone is true; only the claim around step 5's unconditional `.ai/context/` deletion is inaccurate, so reword just that. |
| Hooks don't run under the container lock: a `keep` that lands during `pre-teardown` aborts teardown only after the hook's side effects (m2) | **Document** | Holding the lock across user hooks would deadlock any hook that calls laines. The window is already narrowed. |
| `hooks approve` approves what's on disk when it runs (m2) | **Document**; `--expect <checksum>` deferred post-1.0 | `approve` prints the diffs it approved. A new flag is a minor-version addition, so it can come later without breaking the 1.0 promise. |
| The lanes lock doesn't serialize git activity in the clone between the last fingerprint check and removal (0.4.8) | **Document** | The window is milliseconds and needs a concurrent writer inside the lane being torn down. |
| A Claude `Elicitation`/`ElicitationResult` hook can answer a teardown confirmation (spec §9.5) | **Document** (doctor already warns) | Hooks run as the user; this is the same trust boundary. |
| Deny rules are prefix guardrails. Once on npm, `npx -y …` and `npx …@version` forms also bypass them (C4) | **Document**; Decision D8 on adding rules | Already out of scope in SECURITY. Publishing makes these forms real, so name them. |
| A stale `laines-mcp` keeps running old code after an upgrade; under versioned-path installs (pnpm, volta) the stale check may never fire (0.4.9) | **Document** in the README's MCP section and here | Upgrading over npm makes this common. "Restart your MCP client after upgrading." |
| Case-insensitive disks: a repo tracking `Agents.md` gets the lane-local `AGENTS.md` written over it (m2) | **Fix before 1.0** (§5 F4) | laines would silently modify a tracked file, which an agent might commit. The fix is small. |

**Acceptance:** every row above appears in `SECURITY.md` (or is fixed by §5). The section links the
README Trust model. No item is phrased as a guarantee.

## 5. Deferred-findings triage

**Rule for "fix before 1.0":** it affects correctness or data safety, **or** it changes a surface
